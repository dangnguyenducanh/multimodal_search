# Phase 0: The baseline. ZhichunRoad's code, run as-is, scored by our own scorer

**Goal:** before writing any model code of our own, clone the 5th-place team's released code, train and run it on
our splits, and score it with our own tested nDCG. That number is **the baseline**. Every later phase is judged by how
much it improves on it.
**Sources:** [ZR] github.com/cuixuage/KDDCup2022-ESCI @ `301bb98` (cloned 2026-11-21 into `third_party/zr/`, no
license), paper amazonkddcup.github.io/papers/4952.pdf · SQID paper (arXiv 2405.15190) Table 2 for the scorer anchors.

## Why ZR is the baseline
- It is the best KDD Cup 2022 Task 1 solution **with code**: 5th place, 0.9025 private. The 1st place [www] (0.9043)
  released no code.
- Its README says "ensemble 6 large models" for Task 1. The final `run_origin.py` loads **5**, and we follow the code.
- A baseline we actually ran, on our splits and with our scorer, can be compared fairly. Their leaderboard numbers
  can't: they cover 3 languages on a hidden split.

## Target of this phase
1. The scorer passes its checks (0.1).
2. Their code trains and runs end to end on our data with no logic changes, only the adapters above.
3. The **ZR baseline** (5-member ensemble) has a dev nDCG ± CI, a final-test nDCG, slices, GPU-hours and ms per
   query in RESULTS.md, together with the subset rows (0.6).

## 0.1 Scorer (built first; the baseline is scored with it)
ESCI's official `prepare_trec_eval_files.py` maps S→2 and C→3, then scores `2=0.01, 3=0.1`. Substitute and Complement
gains are therefore swapped (still unfixed on `main`, checked 2026-11-21). The top teams were 0.001–0.005 nDCG apart,
so without a significance test a real gain can't be told from noise.

### `mmsearch/metrics.py`
| Function | Definition |
|---|---|
| `ndcg(labels_in_ranked_order, k=None)` | gains E=1.0, S=0.1, C=0.01, I=0.0; DCG = Σ gain / log2(rank+1); ideal = gains sorted descending. `k=None` scores the full judged list (Task 1 setting) |
| `recall_at_k(ranked_ids, relevant_ids, k)` | used in retrieval (Phase 7), relevant = Exact products |
| `mrr(ranked_ids, relevant_ids)` | used in recommendations (Phase 8) |
| `micro_f1(pred, gold)` | Task 2 (4-class) and Task 3 (substitute vs not) secondary metrics |
| `paired_bootstrap(a, b, n=10_000, seed=0)` | per-query score arrays for the same queries → mean gain, 95% CI, p(gain ≤ 0) |
| `by_slice(scores, slice_labels)` | mean per slice |

**Ties:** sort by score descending, then break ties by `product_id`, so every run is deterministic.

### Splits
Dev = the 2,000 Task 1 US test query ids with the smallest `md5(query_id)`; final test = the other 6,956
(`mmsearch/esci.py: split()`, written once to `runs/p0/splits.parquet`). A hash rather than a seeded RNG, because
numpy doesn't promise identical random streams across versions, and the `zr` env (numpy 1.22) and ours (numpy 2.x)
must agree exactly. Phase 1 reuses the same function, so the baseline and every later phase use the same queries.

### Slices (fixed here, used by every phase)
- query length: 1–2 / 3–5 / 6+ words
- visual-attribute query: contains a color, pattern or material word. The word list is built from the catalog's
  `product_color` values plus a short fixed pattern/material list, and frozen in `runs/p0/visual_words.txt`
- product has an SQID image / doesn't

### Run logging
Every script writes `runs/<phase>/<run>/metrics.json`:
```json
{"phase": "p0", "run": "zr-c123-r12", "args": {...}, "models": [...], "data_version": "esci@<sha256 of examples parquet>",
 "dev": {"ndcg": 0.0, "ci95": [0, 0], "slices": {...}}, "vs_baseline": {"gain": 0, "ci95": [0, 0]},
 "test": null, "gpu_hours": 0, "ms_per_query": 0}
```
It also writes `per_query.parquet` (query_id, score), so any two runs can be compared later without re-running.
`RESULTS.md` is filled only from these files.

### Scorer checks (must pass before any baseline number counts)
| Check | Pass condition |
|---|---|
| `tests/test_metrics.py` | hand-computed lists: all-E; single S vs single C (proves the gains aren't swapped); all-I (nDCG undefined, so defined as 0 and counted); ties |
| random order, full US test (8,956 queries) | mean of 100 shuffles ≈ **0.7483** |
| SQID CLIP text (`data/sqid/query_features` · `product_features.clip_text_features`) | **0.8107 ± 0.002** |
| SQID CLIP image (query text embedding · `clip_image_features`) | **0.8225 ± 0.002** (products with no image score below every imaged product, as in SQID) |
| noise level | dev CI half-width for a typical pair of runs = the smallest gain we can detect |

If CLIP doesn't reproduce, check how products without an image and all-Irrelevant queries are handled before
touching anything else.

## 0.2 Clone and environment
```bash
git clone https://github.com/cuixuage/KDDCup2022-ESCI third_party/zr && git -C third_party/zr checkout 301bb98
conda create -n zr python=3.9 -y
Z=~/miniconda3/envs/zr/bin/python; export PYTHONNOUSERSITE=1   # call the env's python by path, never a bare `pip`
$Z -m pip install torch==2.0.1 --index-url https://download.pytorch.org/whl/cu118
$Z -m pip install transformers==4.18.0 accelerate==0.10.0 datasets==2.3.2 pandas==1.3.5 sentencepiece==0.1.96 \
            scipy==1.7.3 scikit-learn==1.0.2 protobuf==3.19.4 dill==0.3.4 cleanlab==2.0.0 \
            numpy==1.22.4 pyarrow==8.0.0 huggingface_hub==0.10.1 psutil==5.9.0
```
Added pins: `cleanlab` (imported by their filter script, missing from their `requirements.txt`), `numpy<1.23` (needed
by scipy 1.7.3), `pyarrow` (our adapter reads parquet), an old `huggingface_hub` that suits transformers 4.18, and
`psutil` (their predictor). The `xlm-roberta-large` weights are downloaded once as `pytorch_model.bin` (transformers
4.18 can't read safetensors) to `runs/p0/hf/`. Python 3.9 matters: their fold split uses Python's string `hash()`,
and 3.11 changed that hash, so a newer Python would produce different folds.

**Smoke run** (one epoch on 1k train / 500 validation rows, both trainers; done 2026-11-21): both finish, validate and
save a checkpoint. Speed per optimizer step of 256 rows: **fp32 (as they ran it) 16.3–16.8 s, fp16 6.0–6.7 s**.
accelerate's own `MIXED_PRECISION=fp16` switch gives the fp16 run with no code change, so the members train in fp16
(a deviation, listed below). Peak memory ≈ 22.7 GiB per member at their batch of 8, which fits the project's GPU
budget (below) only when it runs alone.

**Project GPU budget (user rule, 2026-11-21): the whole project uses at most 25 GB.** Every GPU job runs alone in one
queue (`scripts/run_all.sh`) under a hard per-process cap, `MMS_GPU_GB=24`: importing `mmsearch` sets PyTorch's memory
fraction, and their unedited trainer runs through `scripts/gpu_cap_run.py`. Two lanes side by side were measured too
(their trainer at batch 2 under 16.5 GB + a proxy run under 7.5 GB: 25,006 MiB together), but batch 2 made their trainer
3× slower (21.6 s per step), so one job at a time is both inside the cap and faster in total.

## 0.3 Data adapter (`scripts/p0_zr_data.py`, run in the `zr` env)
- **Training rows:** `split == "train"`, small and large versions, minus the one query shared with the Task 1 test set
  ([1.md](1.md)). They trained one multilingual model on all three locales (≈ 2.0M pairs). The budget rule in 0.4
  cut this to the **US rows** (1.39M pairs; 1,112,612 in the parts-2–9 training file).
- **Text fields** are capped at 4,000 characters each, which is more than 256 tokens in any of the three languages, so
  the model inputs are unchanged and the CSVs stay small (the disk is 97% full).
- **Renames to their columns:** `product_locale → query_locale`, `product_color → product_color_name`;
  `esci_label` E/S/C/I → `exact / substitute / complement / irrelevant`. Their label ids come from sorting these
  words: complement 0, exact 1, irrelevant 2, substitute 3.
- **Their fold split, same rule as `1_query_hash.py`:** `part = hash(query) % 10` with `PYTHONHASHSEED=12345`.
  Members train on parts 2–9 and validate on parts {0, 1}. For confident learning, each of the five 2-part folds
  {01, 23, 45, 67, 89} gets its own train/valid pair.
- **Validation file capped at 2,000 queries** drawn from parts {0, 1} (≈ 40k pairs). Their trainers validate every
  ~0.1 epoch over the whole file, and on the full parts {0, 1} (≈ 280k US pairs) that would add ~30% to every run.
- **Eval files:** our dev and final-test pairs (US, Task 1 test queries) in the same columns, plus the product
  catalogue CSV that `Task1Predictor.predict()` reads.
- **`brand.txt` / `color.txt`:** exactly as their `3_create_pretrain_data_brand_color.py` builds them: values seen more
  than once in the whole catalogue (punctuation stripped, lowercased), three `[UNK]` lines, then Python-set order
  (fixed by their hash seed). Their model feeds these IDs into its head through fixed-size tables, so a bigger vocab
  crashes. Ours has 151,514 brand lines (their table: 151,519) and 47,036 color lines (theirs: 47,036), so the released
  catalogue is essentially the one they used.
- Output: `runs/p0/zr_data/`.

## 0.4 Train the members (`scripts/p0_zr_train.sh`)
Each member runs from its own copy of their code under `runs/p0/zr_src/<member>/`. In that copy, `sed` edits only
the two vocab paths and, for c2/c3, the field-order line. Every other setting comes from their `run_train.sh`.

| Member | Trainer | Product text order | Train data | Their checkpoint name |
|---|---|---|---|---|
| c1 | 4-class | title · brand · color · bullets · desc (their default) | parts 2–9 | `task01_bs256_0.7540` |
| c2 | 4-class | title · bullets · desc · brand · color (their commented line, `code_task2/run_glue_no_trainer.py:304`) | parts 2–9 | `..._ptbdbc_0.7741` |
| c3 | 4-class | title · desc · bullets · brand · color (their line 305) | parts 2–9 | `..._ptdbbc_0.7729` |
| r1 | regression | default | parts 2–9 | `regression_..._flod20_0.9522` |
| f23 f45 f67 f89 | 4-class | default | 4 more out-of-fold models for confident learning (c1 serves as the fold-01 one) | n/a |
| r2 | regression | default | parts 2–9 minus the rows their filter flags (`label_issue_index.csv`) | `..._after_cf_0.96684` |

**Run order** (each step gives a scorable number while the next one trains):
1. c1 + r1 (first baseline number)
2. c2, c3, which complete their 3-classifier set
3. f23–f89, then their filter script, then r2: the full 5-member ensemble

**Budget:** 1 epoch per member instead of their 10. Their scripts still validate ~10 times inside that epoch and keep
the best checkpoint. That makes 9 model-epochs in total. If they come to more than **~100 GPU-hours**, cut in this
order: first drop the ES/JP rows (−30%), then leave step 3 for last and report the 4-member ensemble.
**Applied 2026-11-21:** the first full run (c1, all locales, fp16) settled at 7.6 s per step on the shared GPU, which
projects to ~120 GPU-hours for the 9 models. So the ES/JP rows were dropped (≈ 85 GPU-hours, about 3.5 days), and
step 3 still runs last.
Their batch sizes fit the 24 GB per-job cap (peak 22.7 GiB); if a member ever has to shrink its per-step batch, raise
gradient accumulation (`BS`/`ACCUM`) to keep their effective batch of 256. Checkpoints are ~2.2 GB each (≈ 20 GB in
total) and go in `runs/p0/zr_models/`. The stages run as `scripts/p0_zr_queue.sh 1|2|3`, interleaved with the other
phases in `scripts/run_all.sh`.

## 0.5 Inference (`scripts/p0_zr_infer.py`, `zr` env)
The script imports their `Task1Predictor` from `third_party/zr/code_evaluation/task1/run_origin.py` and points its five
`model_name_or_path_*` attributes at our checkpoints. On dev and on final test it:
- runs their `predict()` end to end → their ranking file (the output of their code);
- calls their `predict_classification` / `predict_regression` for each member → `runs/p0/member_scores.parquet`
  (query_id, product_id, c1–c3 four-class probabilities, r1, r2). Phase 6 (ensemble), Phase 8 (Task 3 F1) and
  Phase 10 (the baseline column in the demo) reuse this file without a GPU.

## 0.6 Eval (`scripts/p0_score_zr.py`, our env)
- Score their ranking file with **our** nDCG → **ZR baseline, dev** (± bootstrap CI, slices). Final test is scored
  once, for the full ensemble only.
- `mmsearch/ensemble.py: zr_score()` reimplements their `sort_key_4` (gain of the top class × its probability, plus the
  mean regression score). It must reproduce their ranking file **exactly** from `member_scores.parquet`. That makes
  the subset rows trustworthy, and it is Phase 6's starting point.
- Subset rows on dev, with the order their own logs predict:

| Row | Their public-LB log | Expected |
|---|---|---|
| c1 alone | n/a | |
| c1 + c2 + c3 (`sort_key_3`) | 0.8946 | below r1 alone |
| r1 alone | 0.9001 | |
| c1–c3 + r1 | n/a | |
| **c1–c3 + r1 + r2 = ZR baseline** | **0.9032** | highest |

  Their absolute numbers aren't comparable with ours, because they cover 3 languages on a hidden split, start from
  their pretrained checkpoint and ran up to 10 epochs. Only the **order** is a sanity check. If r1 alone doesn't beat
  c1+c2+c3, check the adapter (label words, field columns) before anything else.
- Also logged: Task 2 micro-F1 of the averaged classifiers; Task 3 substitute F1 from P(S) (the baseline for
  [8.md](8.md)); GPU-hours per member; ms per query for the 5 members at their batch size of 32 (the baseline for
  [9.md](9.md)); the dev anchors (random, CLIP text, CLIP image) for scale.

**Deviations, written next to the result in RESULTS.md:** starts from `xlm-roberta-large`, not their pretrained
checkpoint · 1 epoch, not 10 · fp16 mixed precision, not fp32 · US training rows only, not all three locales (budget
rule) · one 10-part hash split for every member (their `flod20` variant isn't in the repo) · no translation or
rebalancing augmentation (it's unclear which members used it; tested in Phase 2) · validation capped at 2,000
queries · the 4-class model class rebuilt from their evaluation copy (`ce-poly-1`) · torch 2.0.1+cu118, not
1.9.0+cu111.

**Checked before the long run** (smoke checkpoints, 30 queries): `p0_zr_infer.py` produces every member's outputs and
their `predict()` ranking file for dev and final test, and `zr_score()` reproduces that ranking **query for query** on
both. So the subset rows and Phase 6 can be computed from the saved outputs.
