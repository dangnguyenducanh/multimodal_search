# Phase 7: Retrieval (first stage)

**Goal:** turn the reranker into a search engine that finds candidates among all 1,215,854 US products.
**Baseline:** the ZR run from [0.md](0.md). **Sources:** 2nd place §2.2 (bi-encoder retrieves, cross-encoder
reranks) · SQID's CLIP embeddings for the image side.

## Their method [ZR]
None. The competition handed each query its ~20 judged products, and `run_origin.py` only reorders that given list.
[www] was the same.

## Their weaknesses
| # | Weakness | Why it matters |
|---|---|---|
| 1 | The system can't search: without someone supplying candidates it returns nothing | a real search engine has to find the candidates itself |
| 2 | A cross-encoder can't score 1.2M products per query | 5 large models × 1.2M pairs is hours per query; a cheap first stage is required |
| 3 | No image path | an image-only match (e.g. color shown in the photo but not in the title) can never become a candidate |

## Our target
- **Recall@100 of each dev query's judged Exact products** clearly above BM25's (CI > 0), so the reranker receives
  the right candidates.
- **End-to-end loss:** the drop from the judged-list nDCG (Phase 6) to retrieve → rerank nDCG@10 is measured and kept small.
- Retrieval p95 latency within the serving budget ([9.md](9.md)).

## Our proposal
| # | Retriever | Representation | Index | Source |
|---|---|---|---|---|
| 1 | BM25 | title + brand + color + bullets (Phase 2 cleaning) | SQLite FTS5 `bm25()`, the same table the backend serves | standard |
| 2 | text bi-encoder, off the shelf | a sentence-embedding model | FAISS HNSW (M 32, efSearch tuned) | 2nd place §2.2 |
| 3 | text bi-encoder, fine-tuned on ESCI train | positives = Exact pairs; hard negatives = Irrelevant pairs + BM25 top hits that aren't Exact; in-batch contrastive loss | same | [ours] |
| 4 | **distilled from our reranker** | the Phase 4/6 reranker scores the bi-encoder's top 100 for train queries, and the bi-encoder learns those scores. The same unjudged pairs become [4.md](4.md) step 7's pseudo-labels | same | [ours] |
| 5 | image | CLIP-L/14 image embeddings (SQID, 192k imaged products), searched with the CLIP text query | FAISS HNSW | [ours] |
| 6 | merge | reciprocal rank fusion (k = 60) of the lists → top 100 → reranker (Phase 6) → top 20 | — | [ours] |

Each retriever is added only if it raises Recall@100 over the previous combination (CI > 0).
**Photo queries** ("snap and search"): CLIP image → image. ESCI has no photo queries, so there's **no ground truth**:
demo only, and labelled that way.

## Eval (dev queries; final test for the winner)
| Metric | Definition | Note |
|---|---|---|
| Recall@100, Recall@1000 | share of each query's judged **Exact** products that were retrieved | valid even though most catalog products are unjudged |
| Recall@100 (E+S) | same, with Substitutes counted | secondary |
| end-to-end nDCG@10 | retrieve → rerank, then drop unjudged products from the list and score | the gap to Phase 6's judged-list nDCG is what retrieval loses |
| latency | p50 / p95 ms per query, retrieval alone and retrieval + rerank | |
| footprint | RAM / disk per index, build time | |

## Output
`mmsearch/retrieval.py` (BM25, encoders, FAISS, RRF), `scripts/p7_build_index.py`, indexes in `runs/p7/`.
