# Phase 9: Backend (FastAPI web service)

**Goal:** serve the trained models as a read-only search service, faithful to the offline scores and fast enough
for a live demo. Kept deliberately small: the project's weight is in Phases 0–6.
**Baseline:** ZR's inference from [0.md](0.md) (`run_origin.py`), whose ms per query is measured in Phase 0.
**Sources:** ETS-Lab README and 2nd/3rd place papers (inference speed-ups); structure follows the Zalo project's
`docs/04-backend.md`.
**Current state:** a BM25-only demo is live, built before any training. What exists, its deviations from this
spec, and how to plug models in are in [demo-handoff.md](demo-handoff.md).

## Their method [ZR]
`Task1Predictor.predict()` is a batch script for the competition harness. It reads the test CSV and catalogue CSV,
pads every pair to 256 tokens, loads the 5 large models **one after another** from disk, writes intermediate
predictions to a temp file, reads them back, and writes one ranking file.

## Their weaknesses
| # | Weakness | Why it matters |
|---|---|---|
| 1 | Offline batch only: no API, no single-query path | it can't answer a user |
| 2 | 5 large models loaded per run, fixed 256-token padding, FP32 | seconds of model loading and most compute on padding; ms per query is far above an interactive budget |
| 3 | Tokenizes the catalogue text on every run | repeated work for text that never changes |
| 4 | Needs the candidate list as input | without Phase 7 there's nothing to rank |

## Our target
- **Parity:** for 500 dev queries the API's reranking of the judged products equals the offline harness's (FP32
  exactly; FP16 nDCG within 0.001).
- **Latency:** p95 of `/api/search` (retrieve 100 + rerank) within a budget set from the Phase 6/7 numbers, at
  batch 1 on the shared GPU; ms per query reported next to ZR's.
- **Robustness and contract** checks below all pass.

## Our proposal
### Run model
- `app/main.py` builds the app (`create_app()`); `uvicorn app.main:app --port 8000` runs it.
- **Startup** (`lifespan`): open SQLite read-only, load the FAISS indexes, load the reranker once (ONNX Runtime FP16
  on GPU, with a PyTorch FP32 path for parity), and load CLIP for photo queries. The app refuses to start if any
  artifact is missing or doesn't match `runs/p9/manifest.json`.
- The built frontend (`web/dist`, [10.md](10.md)) is mounted at `/`; non-`/api` paths fall back to `index.html`. In
  development, Vite proxies `/api` to port 8000.

```text
app/
├── main.py          create_app(), lifespan (load DB, indexes, models), static mount
├── config.py        pydantic-settings, validated at startup
├── db.py            read-only sqlite3 connection per request, row → schema helpers
├── schemas.py       Pydantic response models (mirrored by web/src/types/api.ts)
├── routers/         search.py · products.py · meta.py · compare.py
└── services/
    └── pipeline.py  retrieve → rerank → assemble; imports mmsearch.retrieval / ensemble / recs
```

### Speed-ups vs ZR's inference
| Change | Fixes | Source |
|---|---|---|
| models loaded once at startup, kept in memory | 2 | standard |
| ONNX Runtime FP16 per cross-encoder | 2 | ETS-Lab |
| pre-tokenized product text (memory-mapped `runs/p9/tokens.parquet`) | 3 | ETS-Lab (HDF5) |
| length-sorted batches, dynamic padding | 2 | ETS-Lab, 2nd place §3.4, 3rd place §2.5 |
| skip remaining ensemble members when they can't change the top k | 2 | 3rd place §2.5, adapted |
| LRU cache of recent `(q, mode)` results | — | [ours] |

### Database (SQLite, built offline by `scripts/p9_build_db.py`, never edited by hand)
| Table | Columns | Rows | Used by |
|---|---|---|---|
| `products` | product_id PK, title, brand, color, bullets, description, has_image, image_path | 1,215,854 (US) | every endpoint |
| `products_fts` | FTS5 over title, brand, color, bullets (`bm25()`) | same | BM25 retriever |
| `vec_ids` | faiss_row → product_id, per index | 1.2M / 192k | FAISS hits → products |
| `queries` | query_id, query, query_norm, split | ≈ 84k US | human labels for known queries |
| `judgments` | query_id, product_id, label (E/S/C/I) | ≈ 1.57M US | label badges, examples |
| `baseline_scores` | query_id, product_id, zr_score, ours_score | ≈ 181k (dev + final test) | `/api/compare` (from Phase 0 and Phase 6 saved scores; no ZR model at serve time) |
| `examples` | rank, query_id, reason (`gained` / `lost` / `random`) | 20 | demo example list |
| `models` | name, role (`zr`/`text`/`multimodal`), dev_ndcg, ci_low, ci_high, test_ndcg, ms_per_query | few | `/api/models`, page footer |

### REST API (all under `/api`, JSON, no auth: a read-only public demo with no user data)
| Method | Path | Query / body | Success | Errors |
|---|---|---|---|---|
| GET | `/health` | — | **200** `{status, db, models, gpu}` | 503 |
| GET | `/search` | `q` (1–200 chars), `mode=multimodal\|text`, `k=20` (≤ 50) | **200** `SearchResponse` | 400 |
| POST | `/search/image` | multipart `image` (JPEG/PNG/WebP ≤ 4 MB), `k=20` | **200** `SearchResponse` (`ground_truth:false`) | 400, 413, 415 |
| GET | `/compare` | `q` = a known dev/test query | **200** `CompareResponse`: its judged products with human label, ZR rank, our rank, and both nDCGs | 404 `NO_BASELINE_FOR_QUERY` |
| GET | `/products/{id}` | — | **200** `Product` | 404 |
| GET | `/products/{id}/alternatives` | `k=10` | **200** `{items}`, ranked by P(S) ([8.md](8.md)) | 404 |
| GET | `/products/{id}/goes-with` | `k=10` | **200** `{items}`, ranked by P(C) | 404 |
| GET | `/models` | — | **200** `[{name, role, dev_ndcg, ci, test_ndcg, ms_per_query}]` | — |
| GET | `/examples` | — | **200** `[{query, reason}]` | — |

```text
Product         = {product_id, title, brand, color, bullets, image_url|null}
ProductHit      = Product + {score, probs:{E,S,C,I}, predicted, human_label|null, rank_text_only|null}
SearchResponse  = {query, mode, items: ProductHit[], matched_query_id|null, ground_truth, timings_ms:{retrieve, rerank, total}}
CompareResponse = {query, items: [Product + {human_label, zr_rank, ours_rank}], ndcg:{zr, ours}}
```

`/search` flow: validate and normalize `q` → retrieve ([7.md](7.md): BM25 + vectors, RRF, top 100) → one
`SELECT … WHERE product_id IN (…)` → rerank with pre-tokenized ids → attach `human_label` when `query_norm` matches a
known query → top `k` with timings.

### Errors (one shape)
`{"error": {"code": "VALIDATION_ERROR", "message": "...", "details": [{"path": "q", "issue": "too_long"}]}}`, with
400 `VALIDATION_ERROR` · 404 `PRODUCT_NOT_FOUND` / `NO_BASELINE_FOR_QUERY` · 413/415 `IMAGE_TOO_LARGE` /
`UNSUPPORTED_IMAGE` · 503 `NOT_READY` · 500 `INTERNAL` (logged with a request id, message hidden).

### Security basics
Read-only database (`mode=ro`), no auth and no stored user data, upload size and magic-byte checks before
decoding, CORS only in development, request logs without query text by default.

## Eval
| Check | Pass condition |
|---|---|
| parity | 500 dev queries: API reranking of the judged products = harness ranking (FP32 exact; FP16 nDCG within 0.001) |
| latency | p50 / p95 of `/search`, split into retrieve / rerank, batch 1 on the shared GPU; vs ZR's ms per query |
| compare | `/compare` nDCGs equal the RESULTS.md numbers for those queries |
| robustness | empty / 201-char query → 400; unknown id → 404; 5 MB or non-image upload → 413/415; malformed multipart → 400 |
| contract | `pytest` hits every endpoint and validates against `schemas.py`; the frontend's `types/api.ts` is checked against `/openapi.json` |

`app/`, `scripts/p9_build_db.py`, `scripts/p9_export.py` (ONNX export + parity), `tests/test_api.py`, `runs/p9/`.
