# Phase 2: Preprocessing

**Goal:** turn `runs/p1/` tables into model inputs. Every step is a switch that stays on only if it beats ZR's
preprocessing on dev.
**Baseline:** the ZR run from [0.md](0.md). **Sources:** [ZR] `code_preprocess/` scripts 3–7, `preprocess_function` in
`code_task*/run_glue_no_trainer.py` · [www] paper §3.1 (cleaning, translation, entity markers), §3.2 (input format),
§4 (max length 128).

## Their method [ZR]
| Step | What they do | Code |
|---|---|---|
| Product text | `title </s></s> brand </s></s> color </s></s> bullets </s></s> desc`; field-order variants c2 (title·bullets·desc·brand·color) and c3 (title·desc·bullets·brand·color) for the ensemble | `run_glue_no_trainer.py:237`, `:304–305` |
| Cleaning | HTML tags removed with `re.sub('<.*?>', '', desc)`, **description only**; empty fields → `''`; case kept (lowercasing cost InfoXLM ~0.1%) | same |
| Length | `max_length=256`, `pad_to_max_length`, `truncation=True` (longest-first, so a long query can be cut too) | `run_train.sh`, tokenizer call |
| Translation | ES/JP train rows → English with MarianMT opus-mt, weight 0.3 | `4_translation_es_us.py` |
| Rebalance C / I | extra Complement/Irrelevant pairs whose product text is bullets + description only (≈ 800 chars EN/ES, 360 JP), weight 0.3 | `6_rebalance_negative_samples.py` |
| Label-noise filter | 5 out-of-fold models → cleanlab → drop the ~4% of rows that look mislabelled | `7_confidient_learning_filter.py` |
| Vocabularies | brand and color IDs; char 3-gram vocab with word2vec-initialized bag embeddings (for their `_Bag` model) | `3_create_pretrain_data_brand_color.py`, `5_tokenizer_n-gram.py`, `word2vec/` |

## Their weaknesses
| # | Weakness | Why it matters |
|---|---|---|
| 1 | They never measured what 256 tokens cuts off. The bullets come before the description, so long descriptions are mostly lost, and longest-first truncation can cut the query | information the model never sees; the query is the one field that must survive |
| 2 | Every pair is padded to 256 tokens, even short ones | most of training and inference compute goes to padding (GPU-hours, ms per query) |
| 3 | HTML is cleaned in the description only; symbols and emojis stay | noise tokens in titles and bullets |
| 4 | Translation, rebalancing and the filter were **never measured alone on Task 1 nDCG** | each costs compute (the filter needs 5 extra trainings), and none is known to help |
| 5 | Rebalanced pairs are synthetic (no title in the product text) | training sees a text format it never meets at test time |
| 6 | The filter drops rows the models disagree with, including hard but correct S/C cases | [www] kept those rows and used soft labels instead (Phase 4), which gained +0.0022 together with pseudo-labels |
| 7 | Nothing on the query side ([www] marked product/brand mentions) and no images | the query is the shortest, most ambiguous input |

## Our target
- Measure truncation, then fix it: **0% of queries cut**, and the share of products losing a whole field reported per length.
- **Same or better dev nDCG at fewer GPU-hours** than ZR's preprocessing. Dynamic padding must not lose (CI lower
  bound > −0.002) and should cut training time substantially.
- Each ZR augmentation stays only if it wins alone; otherwise it's dropped and the compute is saved.

## Our proposal (each a switch, tested one at a time at proxy scale, [4.md](4.md) §4.0)
| # | Change vs ZR | Fixes | Source |
|---|---|---|---|
| 1 | Measure: % of pairs truncated at 128 / 256 / 384, and which fields get cut | 1 | [ours] |
| 2 | `truncation="only_second"`: never cut the query | 1 | [ours] |
| 3 | Dynamic padding + length-sorted batches instead of a fixed 256 | 2 | ETS-Lab, 2nd/3rd place |
| 4 | Length 128 [www] / 256 [ZR] / 384. Dynamic padding makes longer inputs cheaper, so 384 becomes affordable | 1 | both + [ours] |
| 5 | Format A: `color: {c} brand: {b} description: {title} {bullets} {desc}` [www] vs ZR's format B | 1 | [www] |
| 6 | Field budget: title kept whole, then a fixed token budget per field (e.g. bullets 96, description 96) instead of first-come truncation | 1 | [ours] |
| 7 | Cleaning on every field: HTML, symbols, emojis, collapsed whitespace | 3 | [www] |
| 8 | ZR translation (switch); if it wins, also try 0.3 vs 0.5 weight | 4 | [ZR] |
| 9 | ZR rebalance (switch), plus a variant that keeps the title in the synthetic text | 4, 5 | [ZR] + [ours] |
| 10 | ZR confident-learning filter (switch) vs keeping all rows and using soft labels (Phase 4 step 6) | 4, 6 | [ZR] vs [www] |
| 11 | Entity markers on the query: `[Product] iphone 8 plus [/Product]`, tagged with an off-the-shelf NER model plus the catalog brand list | 7 | [www] |
| 12 | Images: download the SQID URLs → `data/images/`; one caption per image → `runs/p2/captions.parquet` (for Phase 5) | 7 | [ours] |

Label ids: [ZR] uses complement 0, exact 1, irrelevant 2, substitute 3. We use E 0, S 1, C 2, I 3 everywhere and
convert at the boundary with their code.

## Eval
- **Data report** (`runs/p2/report.json`): % truncated per length and field, % empty per field, rows added by
  translation/rebalancing, rows removed by the filter, image download success rate.
- **Value checks:** each switch vs the previous configuration on dev (paired bootstrap at proxy scale). Losers are
  switched off and the decision goes in RESULTS.md, including GPU-hours saved or spent.
- **Phase result:** the best preprocessing vs ZR's preprocessing, same proxy model: dev gain ± CI and training
  time ratio.

## Output
`mmsearch/text.py` (`clean()`, `product_text(fmt, field_budget)`, vocab builders), `mmsearch/augment.py`
(`translate()`, `rebalance()`, `confident_filter()`), `scripts/p2_preprocess.py`, `runs/p2/`.
