# Phase 1: Data

**Goal:** fixed tables and splits that every later phase reads. They are built once, never changed, and reproducible
on any machine.
**Baseline:** the ZR run from [0.md](0.md). **Sources:** [ZR] `code_preprocess/1_query_hash.py`,
`code_task1/run_glue_no_trainer.py` (sample weights) · [www] paper §3.1 · our data checks of 2026-11-21.

## Inputs (already downloaded, read-only)
| File | Rows | Key columns |
|---|---|---|
| `data/esci/shopping_queries_dataset_examples.parquet` | 2,621,288 | query_id, query, product_id, product_locale, esci_label, small_version, large_version, split |
| `data/esci/shopping_queries_dataset_products.parquet` | 1,814,924 (1,215,854 US) | product_id, product_title, product_description, product_bullet_point, product_brand, product_color, product_locale |

| `data/sqid/query_features.parquet` / `product_features.parquet` | 8,956 / 164,900 | CLIP-L/14 768-d text / image embeddings |

## Their method [ZR]
- **Pool:** the `train` rows of all three tasks and all three locales (US, ES, JP), joined to products on
  `(locale, product_id)`. [www] did the same.
- **Folds:** `part = hash(query) % 10` with `PYTHONHASHSEED=12345` (Python's built-in string hash). Parts {0, 1} are
  their validation set. A 20-part variant (`flod20`) was used for some members, but it isn't in the repo.
- **Sample weights:** 0.3 by default, set to 1.0 when `query_locale ∈ {us, es, jp}`. Original rows get 1.0, translated
  or synthetic rows 0.3.
- **Model selection:** the best checkpoint by validation on parts {0, 1}, read every ~0.1 epoch.

## Their weaknesses
| # | Weakness | Why it matters |
|---|---|---|
| 1 | Folds come from Python's salted `hash()`. They only reproduce on Python < 3.11 with the seed set, and the 20-part split is lost | splits can't be rebuilt from the repo alone, so other people can't check out-of-fold work |
| 2 | Validation is drawn from **train** queries: E 69.6 / S 19.7 / I 8.6 / C 2.1 %, 20.8% of products imaged | test looks different (E 43.9 / S 35.0 / I 16.7 / C 4.5 %, 95.2% imaged), so checkpoint selection optimizes for the wrong label mix |
| 3 | One validation number, read about 10 times per epoch, no confidence interval | the best of ~10 noisy readings is biased upward, and nothing separates a real gain from noise |
| 4 | Three locales feed a model whose target is US English; whether ES/JP helps US was never measured | the extra rows cost about 30% more training time for an unknown gain |
| 5 | No image data (it didn't exist in 2022) | the multimodal phases have nothing to join |

## Our target
- Same raw data, but **every split is deterministic on any Python version** and is checked by the counts below.
- **Every comparison (ZR included) runs on the same 2,000 dev queries**, which have test's label mix and image
  coverage. The final test (6,956 queries) is used only to report phase winners.
- A measured answer to "do ES/JP rows help US?" (weakness 4). They are kept only if they win.

## Our proposal
| # | Change vs ZR | Fixes | How it's checked |
|---|---|---|---|
| 1 | Stable folds: `fold = int(md5(query).hexdigest(), 16) % 10`. All pairs of a query share a fold. The 3 folds for self-distillation [www], 7 for bagging [www] and 5 fold pairs for confident learning [ZR] all derive from these 10 | 1 | rebuilding gives byte-identical assignments; no query appears in 2 folds |
| 2 | **Dev = the 2,000 query ids with the smallest md5(query_id)** among `small_version == 1 & split == "test" & locale == "us"`; **final test** = the other 6,956 (`split()` is written in Phase 0 and reused here; a hash, not a seeded RNG, so every numpy version agrees) | 2 | label mix and image coverage of dev match test within 1 point |
| 3 | Checkpoints, ladder steps and ensemble weights are all chosen **on dev**; final test is opened once per phase winner | 2, 3 | the ZR baseline (picked on its own train validation) and our models are both reported on final test, which neither has touched. Our dev gains carry a small selection bias, and final test removes it |
| 4 | Decisions use the paired bootstrap on dev ([0.md](0.md) §0.1); the noise floor (CI half-width) is published in RESULTS.md | 3 | — |
| 5 | Pool choice: **US only** vs **US + ES/JP** (ZR's choice), trained at proxy scale ([4.md](4.md) §4.0) and compared on US dev | 4 | paired gain, CI > 0, or the cheaper pool (US only) stays |
| 6 | Join SQID: `image_url`, `has_image`, and CLIP query/image embeddings (US) | 5 | coverage per split in the report |
| 7 | Keep ZR's weight rule (original 1.0, augmented 0.3) as a column. Phase 2 tests the 0.3 value | — | — |
| 8 | Drop the one query shared between train and the Task 1 test set | leakage | 0 queries shared between train, dev and final test |

## Splits (result)
| Split | Rule | Size (US) |
|---|---|---|
| train | `split == "train"`, small **and** large versions, minus the one shared query | 74,888 queries · 1,393,063 pairs |
| dev | 2,000 queries (smallest md5 of query_id) from the Task 1 US test set | 40,428 pairs |
| final test | the other 6,956 Task 1 US test queries | 141,273 pairs |
| optional extra train | ES / JP train rows (kept only if proposal 5 wins) | ≈ 0.59M pairs |

Checked: train ∩ Task 1 test has 0 query–product pairs. 38.8% of test *products* also appear in train under other
queries, which is normal and allowed. Dev is drawn from test because only 260 Task 1 train queries have images for
≥ 90% of their products, while 95.2% of test pairs are imaged.

## Eval (pass all)
- dev + final test = **8,956 queries / 181,701 pairs**; train = 74,888 / 1,393,063 (minus the dropped query)
- 0 queries shared between train, dev and final test; 0 queries split across two folds
- label mix: test E 43.9 / S 35.0 / I 16.7 / C 4.5 %; train E 69.6 / S 19.7 / I 8.6 / C 2.1 %
- image coverage: test 95.2%, Task 1 train 30.0%, all train 20.8%
- rebuilding on Python 3.9 and 3.12 gives byte-identical split and fold assignments
- proposal 5 decided and logged in RESULTS.md
